# SenseEase — Master UX Audit (Alpha-1)
**UX Director review · Apple HIG + ui-ux-pro-max · Quiet Guardian posture**
*Synthesized from seven surface audits, cross-checked against the live tree (`src/SenseEase.App/…`, not worktrees), 2026-06-06.*

---

## 1. Executive Summary

SenseEase has an **exceptional design *intention*** and a **half-shipped design *execution***. The conceptual core — a "Quiet Guardian" that speaks in app-action plain language ("Watching your screen", "Easing your view"), bands strain into calm earth-tones, and never uses alarm red — is genuinely Apple-grade and clinically literate. The token architecture, the comfort-hero converter pattern, the motion restraint on the ambient bar, and the calibration state machine are all real strengths.

But the gap between the locked direction and the shipping XAML is wide enough that **the product is not yet Apple-grade for an anxiety- and vestibular-sensitive audience.** Five experience-level problems cut across every surface:

1. **Accessibility is intent-only, not implemented.** Zero `prefers-reduced-motion` handling exists in the entire codebase (`Grep` for `ClientAreaAnimation|UserPreferenceChanged` → 0 files). Zero keyboard focus indicators exist (`FocusVisualStyle|IsFocused` → 0 matches in any XAML). The typing animation, bar hover, and mask cross-fade all run unconditionally — **the app that exists to reduce VIMS can itself trigger VIMS** for a user who has explicitly set Reduce Motion in Windows. This is the single most damaging contradiction in the product.

2. **The design system is documented but not enforced — and the live code already violates its own locked constraints.** `SenseEaseTheme.xaml:11` literally declares *"Calm palette only: NO #E54747, NO #024AD8, NO #7B8DB0."* Yet `#E54747` appears **6× in the live `MainWindow.xaml`** (and 1× in the theme itself), and `#024AD8` royal blue is used throughout. The lint gates described in the plan (orphan-hex ratchet, banned-phrase gate) are not catching this. The single source of truth has already drifted.

3. **The notification card — the one moment of contact with a user who feels worst — presents up to 8 interaction targets at once, including a chat input that the spec explicitly deferred to Alpha-2.** The `ChatInputBox`/`ChatSendBtn` are live and fully visible at `NotificationCardWindow.xaml:401/431` (placeholder "跟 SenseEase 說話" at :415), *not* collapsed. A nauseated user is asked to choose between Engage, Dashboard, Mute, Power-Save, a 4-cell discomfort ramp, and "talk to the bot." This is choice overload at the exact moment the posture demands one effortless action.

4. **Auto-pop modal behavior is unsafe and self-contradictory.** The card is `Topmost=true` yet `ShowActivated=false`, polls the foreground at 500 ms, and can auto-hide before a slow-reacting anxious user has read it — while also being force-Activated by the host. It feels modal (hijacks the screen) and ambient (vanishes silently) at once. For the target user, sudden appearance + sudden disappearance is a startle/anxiety generator.

5. **Telemetry leaks back into "calm" surfaces, and color is doing accessibility work alone.** Raw numbers (OFI, Pressure) still occupy premium space on the Dashboard Event Log and dominate the Eye-Protection tab; the comfort chips and ComfortMeter rely on near-invisible "Weak" fills (`ComfortSteadyWeak #E2F0EC`, `ComfortRisingWeak #F6ECD8` ≈ 1.1–1.3:1 on white) with no icon or border redundancy, failing `color-not-only` for colorblind/low-vision users.

**Verdict:** *Direction is Apple-grade; execution is Alpha-grade.* The path to Apple-caliber is not a redesign — it is **finishing the design that is already specified**, closing the a11y floor, and enforcing the tokens the team already locked. Do not add features until findings C1–C5 are closed.

## 2. Prioritized Findings (deduped & merged across surfaces)

### 🔴 CRITICAL

**C1 — No `prefers-reduced-motion` support anywhere; clinical app triggers the symptom it treats**
- **Surfaces:** MainWindow typing-dots (`MainWindow.xaml` Storyboard ~817–830), PersistentBar hover (`AnimateHoverTransition`), OverlayWindow mask cross-fade (`MaskSmoothingFactor=0.25`), calibration card transitions.
- **Evidence:** `Grep ClientAreaAnimation|ReducedMotion|UserPreferenceChanged` over all `.cs` → **0 files**. `PersistentBarWindow` registers `SystemEvents.UserPreferenceChanged` but never reads the motion flag.
- **Guideline:** `reduced-motion` (CRITICAL) · WCAG 2.1 §2.3.3 · Apple HIG Reduce Motion. Note: the clinical mask cross-fade is *correctly* exempted per LOCKED_DIRECTION — but decorative chrome is not.
- **Fix:** Add an `AccessibilityHelper.GetReducedMotionEnabled()` reading `SystemParametersInfo(SPI_GETCLIENTAREAANIMATION)`. Gate every decorative Storyboard: if reduced, snap to target (no animation). Wire the already-registered `UserPreferenceChanged` to re-evaluate mid-session. Keep the ≥300 ms mask ease exempt.
- **Effort:** m

**C2 — No keyboard focus indicators on any interactive element**
- **Surfaces:** every Button/CheckBox/RadioButton/Slider across MainWindow, NotificationCard, Settings, Calibration.
- **Evidence:** `Grep FocusVisualStyle|IsFocused` over all XAML → **0 matches**. Templates have `IsMouseOver`/`IsPressed` triggers only.
- **Guideline:** `focus-states` (CRITICAL) · WCAG 2.1 §2.4.7 · Apple HIG Focus.
- **Fix:** Define one shared `FocusVisualStyle` (2–3 px solid Accent ring + 1 px inset, *not* dashed gray) in the theme; apply to all button/checkbox/radio/slider styles. Verify Tab order matches visual reading order; add Escape-to-dismiss on the card and banners (no keyboard trap, §2.1.2).
- **Effort:** m

**C3 — Borderline/failing text contrast on body, helper, and comfort-chip text**
- **Surfaces:** theme tokens + chips. Confirmed values: `TextSecondary #525B6B`, `TextTertiary #6E7787`, `CardLabel #7B8DB0`; "Weak" comfort fills `#E2F0EC / #F6ECD8 / #F6E2DE` are ~1.1–1.3:1 on white.
- **Guideline:** `color-contrast`, `color-accessible-pairs` (CRITICAL) · WCAG §1.4.3.
- **Fix:** Darken `TextSecondary→~#4A5B6E`, `TextTertiary→#5A6B7A`, retire `CardLabel #7B8DB0` (also a banned token per theme header line 11). Strengthen Weak fills (`ComfortSteadyWeak→#C7E5DB`, `ComfortRisingWeak→#F4E0C5`, `ComfortHighWeak→#EDCFC6`) and add a 1.5 px full-color border so the chip reads without relying on fill luminance. Re-verify all three bands hit 4.5:1 on both white and `SurfaceMuted`.
- **Effort:** m

**C4 — Notification card: cognitive overload + chat row shipped against spec**
- **Surface:** `NotificationCardWindow.xaml` — 6-row grid presents title+telemetry, proposal, comfort description, 4-cell discomfort ramp, 3 action buttons, Power-Save, settings/close, **and a live chat input**.
- **Evidence:** `ChatInputBox` (:401), `ChatSendBtn` (:431), placeholder "跟 SenseEase 說話" (:415) are **fully visible** — only the proposal-safety elements (:151/:184) are `Visibility="Collapsed"`. Spec defers chat to Alpha-2.
- **Guideline:** `progressive-disclosure` (Priority 8) · Apple HIG Minimize Choices · Quiet Guardian single-action mandate.
- **Fix (low-risk, spec option A):** Set `ChatInputBox`/`ChatSendBtn`/`ChatStatusText` to `Visibility="Collapsed"` + `IsHitTestVisible="False"` so the quick-response send path still compiles, but no chat affordance shows. Restructure to a strict 4-zone hierarchy: Header → (conditional) Proposal → Comfort chip → single full-width **Ease** hero. Demote ramp/Power-Save/Dashboard/Mute below the hero or behind idle-reveal.
- **Effort:** s (collapse) + m (re-zone)

**C5 — Auto-pop card behavior is unsafe and modally self-contradictory**
- **Surface:** `NotificationCardWindow.xaml.cs` (foreground poll ~405–440, idle-fade ~544–566) + `MainWindow.xaml.cs` spawn (~889–999, including `Activate()` at ~999).
- **Issue:** `Topmost=true` + 500 ms foreground poll + auto-hide-on-focus-loss + host `Activate()` together steal focus, then vanish before a slow user reads the card. EM5 gate (`_userHasInteracted && _activeProposal is null`) protects proposal cards but leaves non-proposal auto-pops vulnerable.
- **Guideline:** `modal-vs-navigation`, `escape-routes` (Priority 9) · Apple HIG user-initiated, non-modal notifications.
- **Fix:** Commit to **ambient**: drop `Topmost` unless a proposal is pending; remove the aggressive 500 ms foreground hide; widen the survive-window to ≥10 s for *all* auto-surfaced cards; remove `Activate()` for non-proposal cards. Keep idle-fade as the only dismiss path + always-available manual close. Strongly consider making the card **user-initiated** (click bar/tray) as the product default.
- **Effort:** l

- **Evidence:** `SenseEaseTheme.xaml:11` bans `#E54747`/`#024AD8`/`#7B8DB0`; `Grep #E54747` → **6× in live MainWindow.xaml + 1× in the theme file itself**; `#024AD8` used across tabs/buttons; `CardLabel #7B8DB0` still defined. NotificationCard uses a *different* blue (`#1E5BB0`) than MainWindow.

**H2 — Minimal `AutomationProperties` across surfaces; screen-reader users blind to most controls**
- **Evidence:** only ~2 `AutomationProperties.Name` in the whole app (MainWindow hero ~230/285). NotificationCard close `×` / settings `⚙`, Settings form fields, OverlayWindow, PersistentBar all unlabeled. Card icon buttons are 22×22 (below 44×44).

- **Fix:** Add `AutomationProperties.Name`/`HelpText` to every icon-only and dynamic-status element (start with NotificationCard → Overlay → Settings). Bind dynamic names to comfort/tier props. Bump card close/settings to 44×44, drop the redundant tooltip-as-a11y.

**H3 — Information hierarchy fragments below the hero; sections read as a flat checklist**

- **Fix:** Re-tier: reuse the D1 hero headline+subline+chip at top; move the 5-column metrics into a collapsed "Advanced" Expander (mirror the Dashboard pattern). Raise all 11 px → 12 px floor.
- **Effort:** m

**H5 — Event Log (raw OFI/Pressure) occupies 200 px of premium Dashboard space, duplicated on Eye-Protection**

- **Guideline:** `information-architecture`, `progressive-disclosure` · Quiet Guardian no-obsessive-monitoring.

## 3. Per-Surface Verdict

- **Home / Dashboard:** *Strong lead, fragmented body.* The comfort hero is the gold standard of the whole app — keep it verbatim. Below it, the rhythm collapses into a flat checklist (H3), the Event Log claims premium space for raw telemetry (H5), the ComfortMeter has an unexplained 0–100 scale (M1), and there are zero focus rings (C2). **State: ship-blocking on a11y, otherwise a layout pass away from excellent.**

- **Other console tabs (Eye-Protection / AI Assistant / Settings):** *The calm posture stops at the Dashboard edge.* Eye-Protection regresses to a numeric dashboard with a raw `Canvas` chart (H4, H6); Settings is a wall of 11 px helper text with no grouping and a palette-breaking amber button (M3, H1); AI Assistant is solid but lacks auto-scroll and followup affordance (L1, L9). **State: needs the hero/disclosure pattern propagated and a token cleanup.**

- **Popup notification card:** *The riskiest surface for this audience, and the least finished.* Eight competing targets, a chat row shipped against its own spec (C4), and auto-pop behavior that startles then vanishes (C5). The *spec* is excellent; the *implementation* hasn't caught up. **State: ship-blocking — requires re-zoning + ambient behavior + chat collapse before Alpha.**

- **Ambient (bar / tray / overlay):** *The crown jewel.* Rigorously calm — 0.00 alpha at rest, no decorative motion, distinct Fault/Paused affordances, single-source tier→color. Only refinements remain: DPI/alpha legibility (M11), amber color-distance (M12), outline weight (M13), reduced-motion on hover/mask (C1). **State: closest to Apple-grade; polish, don't rebuild.**

- **Calibration / onboarding:** *Architecturally clean, emotionally under-supported.* Excellent VM state machine, bilingual, safety-floor crisis handling. But the first-run banner alarms (M2), the 7-checkbox cards overwhelm, intensity selection lacks feedback, and there's no completion confirmation (M14). **State: solid bones, needs reassurance microcopy + feedback polish.**

- **Design system / plan:** *Best-in-class on paper, unenforced in practice.* Token spec, motion hierarchy (clinical > chrome), bilingual decoupling, triple-coded status, and lint *design* are all exemplary. But the lint isn't gating the build, the live tree already violates the locked palette (H1), and a11y is specified-but-absent. **State: production-ready as a document; not yet load-bearing as code.**

## 4. What to KEEP (do not regress)

1. **The comfort-hero converter pattern** (`TierToHeadline/Subline/ComfortBand/Label`, all `Mode=OneWay`) — centralizes tier→band logic, prevents threshold drift, speaks app-action voice. The template for every other surface.
2. **The calm palette discipline** — no alarm red *in the token layer*, muted clay `#B65C4E` for high strain, earthy bands. (Now enforce it in MainWindow too.)
3. **Ambient bar restraint** — 0.00 alpha at rest, 0.92 peak (no black wall), motion only on hover, distinct Fault(solid)/Paused(dashed) outlines, snapshot-based flicker prevention.
4. **Single-source `TierColorPalette`** feeding bar + tray + future surfaces.
5. **Advanced Expander demotion** of raw telemetry with byte-identical bindings (no deletion).
6. **Calibration VM/View separation** + mutual-exclusion logic + hardcoded crisis-line safety floor.
7. **Motion hierarchy** that exempts the clinical mask cross-fade from Reduce-Motion while governing decorative chrome.
8. **Bilingual coverage** and the `.resx`-per-language plan.
9. **Proposal flow** (Accept/Decline/Later, conditional render, expiry-disables-all).
10. **The Voice & Tone guide** and the personality heuristic ("Would this calm a nauseated person about to get a migraine?").

Phase 3 items (14–17) are the only ones that **require the user's visual sign-off or live-user validation** — do not self-certify color/tone/posture choices for this audience.

## 6. Design-System Gaps (to reach Apple-grade)

- **Enforcement, not just specification.** The biggest gap: the lint gates exist in the *plan* but the live tree already violates the locked palette (`#E54747` ×6 in MainWindow, `#024AD8` throughout, `CardLabel #7B8DB0` still defined). Until lint **fails the build**, the "single source of truth" is fiction.
- **Motion tokens are under-specified for reduced-motion.** There is a `Dur.base`/`Dur.ui` scale and a clinical-exempt rule, but **no implemented reduced-motion switch** and no per-animation classification (decorative vs clinical) in code. Add a `MotionPolicy` helper + a token-level `IsDecorative` convention.
- **Focus & a11y are not part of the system.** No `FocusVisualStyle` token, no shared accessible Checkbox/Radio/Slider styles, no automation-name convention, no `BINDING_CONTRACTS.md` enforcing `VimsTier` OneWay. Promote a11y from "applied on hero" to a system primitive every control inherits.
- **Color semantics need redundant-coding baked in.** "Weak" fills fail as standalone signals; the system should *require* icon+label+border with every comfort/danger color (the docs say this; the components don't yet). Document the `Danger`≡`ComfortHigh` overload note so no one "brightens" Danger.
- **Contrast pairs need a published, tested matrix.** Several shipping tokens (`TextSecondary`, `TextTertiary`, all Weak fills) are borderline/failing — the AA/AAA table in the doc describes the *aspiration*, not the *current* values. Re-derive and lock.
- **No dark mode / Dynamic Type story.** Tokens are single-mode; FontSizes are hardcoded. For Apple-grade, define Light/Dark variants and bind type to OS scaling (M17).
- **Type scale floor is enforced on the Dashboard but leaks elsewhere** (11 px on Eye-Protection/Settings). Make the 12/13/14/16/20/28 scale a hard lint (`no 10/11px`) as the plan describes.
- **Trade-off documentation.** Name the negotiated decisions (`ComfortRising #9A6B22` AA-over-saturation; `Danger`≡`ComfortHigh`) inline so a future contributor can't silently regress them.

---

*Bottom line: SenseEase's design thinking is genuinely Apple-caliber for this audience — the problem is that ~40% of it lives in specs and locked-direction docs while the shipping XAML lags behind, and the accessibility floor (reduced-motion, focus, contrast, automation) is essentially unimplemented. Close C1–C5 and enforce H1 before any new feature work; the rest is a finishing pass on a fundamentally sound, humane design.*

- **[LOW] Proximity polling at 60 Hz on every frame is overkill; can degrade on battery/low-power scenarios**

The power cost is negligible per the code comment, but on battery-powered thin clients or in ultra-low-power scenarios (e.g., users with vestibular conditions who may be on medication or fatigued), the sustained ~60 Hz timer can contribute to CPU spinup and prevent deeper power-state transitions. ## SenseEase first-run / onboarding + calibration questionnaire flow (CalibrationCardView.xaml, MainWindow.xaml first-run banner, CalibrationCardViewModel, docs/CALIBRATION.md)

**Strengths:** Architectural strength: The 5-card sequential state machine in CalibrationCardViewModel is clean, testable, and aligns with Apple HIG principles of progressive disclosure via card-based flows (similar to iOS multi-step onboarding). The VM is fully decoupled from the view, making it easy to test without WPF dependencies.; Calm palette and type system: The SenseEaseTheme.xaml is well-designed for an anxiety-sensitive app — soft colors (#2F7D6E, #B65C4E, #3A6EA5), generous line-height (1.5-1.75 equivalent via 20/22/28/34px for body/heading/title/display), and a clear type hierarchy (Type.Display, Type.Title, Type.Heading, Type.Body, Type.Caption). This prevents data corruption and aligns with the spec's intentional design. The logic is tested (CalibrationCardViewModelTests mentioned in CALIBRATION.md).; Optional fields and skip-ahead design: Spec §3 and the VM implementation both embrace optionality — Q1, Q2, Q4, Q5 are skippable; only Q3 is mandatory (with a fallback UI for low-confidence LLM paths). This reduces friction on a baseline measurement. SenseEase's "Calm" design system and M5 implementation plan are exceptionally mature, evidence-grounded, and clinically-sound.
